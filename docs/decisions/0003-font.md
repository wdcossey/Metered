# ADR 0003: the font, substitutes for Uber Move

Status: accepted, 2026-11-16. Measured with `tools/reference/fonts.js`; the numbers below are its
output, and `tools/reference/fonts.g.json` holds every measurement (generated: run the tool, never
edit it).

## Context

Base Web's `primaryFontFamily` is `UberMoveText, system-ui, "Helvetica Neue", Helvetica, Arial,
sans-serif` and its `secondaryFontFamily` `UberMove, UberMoveText, …`
(`baseui/themes/shared/typography.js`; `move-theme/typography.js` changes only which styles use which).
The ramp draws UberMoveText at 400 (`font100` to `font400`, the Paragraph styles) and 500
(`font150` to `font450`, the Label styles, which a Button's label uses), and UberMove at 700
(`font550` to `font1450`, Heading and Display). Uber Move is proprietary and can't ship.
baseweb.design serves it as web fonts, so it can be measured, though nothing of it may be kept.

Metered drew Inter (Avalonia.Fonts.Inter, Inter 3.019), which Base Web's stack reached by falling
through to the default font. The question is whether an OFL font matches Uber Move better, measured
the way a Button's width and its text's baseline depend on it.

## How it was measured

One engine for both sides: headless Chromium (Playwright, Chromium 141) on
`https://baseweb.design/components/button/`.

- **The reference** is Uber Move as the page's own `@font-face` rules load it, in an off-the-record
  context with the cache disabled. Only measurements of laid-out text leave the page.
- **The candidates** are loaded into the same page from their bytes (`FontFace`): static instances
  at 400, 500, 600 and 700 (Fontsource 5.3.0, the Latin cut Google Fonts' API makes of each
  family's font), the leaders also from their own repositories' static TTFs at a pinned commit (the
  files embedded here), and Inter out of Avalonia.Fonts.Inter 12.1.4.
- **Widths**: 21 strings laid out at 1000 px with kerning, in em: twelve button labels, three
  sentences, digits and prices, capitals, the lowercase alphabet. The error is candidate / Uber Move
  − 1, per string; per weight, the mean of its absolute value and the worst. Labels are also laid
  out at the Button's own sizes (`LabelXSmall` to `LabelLarge`: 12, 14, 16, 18 px).
- **Vertical**: cap height (H), x-height (x), ascender (d) and descender (p) from the ink at 1000 px;
  the engine's ascent and descent from the laid-out content area; the baseline in a line box at each
  of the ramp's 18 sizes and line heights. For each candidate the tool also reads the metrics
  Avalonia 12 uses (`GlyphTypeface`: OS/2 typo when `USE_TYPO_METRICS` is set, else `hhea`) and
  places the baseline as Avalonia does, the extra leading split evenly.

### That Uber Move was really what was measured

- `document.fonts` reports each face `loaded`; the rules register UberMove and UberMoveText at 200,
  400, 500 and 600 (the files named `-Bold` at 600).
- Chromium's own record of the platform font that drew each face's text (DevTools'
  `CSS.getPlatformFontsForNode`, over all 21 strings): `UberMoveText-Regular` at 400,
  `UberMoveText-Medium` at 500, `UberMove-Bold` at 700, each a custom font and the only font used.
- Every width is the same with `monospace` or `serif` after the family: no glyph fell back.
- UberMove at 700 and at 600 draw identical widths and cap heights: 700 draws the Bold file, with
  no synthesised emboldening.

The shortlist: Inter, the incumbent, and its newer cuts (Inter 4, Inter Tight); the neo-grotesques

Text); the families with a width axis, in case a narrower width fitted UberMove (Instrument Sans,
Mona Sans, Archivo, IBM Plex Sans, Roboto); and families cut, as Uber Move is, as a text and a
display pair. All but Be Vietnam Pro are variable fonts at Google Fonts; each was measured as the
static instance Avalonia would draw.

## Decision

1. **UberMoveText draws in Instrument Sans; UberMove draws in Figtree.** Two families, because Base
   Web has two and they differ by 7.7% in width. Instrument Sans has the lowest width error on both
   text faces; Figtree on the display face. Together they score 1.19% over the three ramp faces,
   against 2.26% for the best single family and **4.81% for Inter**: four times smaller.
2. **Embedded as static TTFs** from each family's own repository, at 400, 500, 600 and 700, with its
   `OFL.txt` beside them in `fonts/`. Avalonia 12.1.4 reads neither WOFF2 nor a variable font's
   axes, so the variable fonts aren't an option. Eight files, 578 KB, where Avalonia.Fonts.Inter
   carried six weights in 1.9 MB.
3. **Base Web's names stay in the tokens.** The generated `typography.*.fontFamily` keep
   `UberMoveText, …` and `UberMove, …`; the app maps the two names with Avalonia's
   `FontManagerOptions.FontFamilyMappings`, which applies to a family's first name. The tests
   (`Harness/TestApp.cs`) and the desktop sample (`Program.cs`) do this; `Avalonia.Fonts.Inter` is
   gone from both. The sample also makes Instrument Sans the default family, for the text
   `SimpleTheme` draws; the tests leave the default to the platform, because Avalonia falls back to
   the default for a family it can't find, and a default of Instrument Sans would hide a missing
   UberMoveText mapping.
4. **No width axis instance.** Instrument Sans SemiCondensed, the nearest static width, is 8.1%
   narrow on UberMove. A custom instance between would be a Modified Version under the OFL, under
   another name, to fit one face that Figtree already fits within 1.4%.

## What stays wrong

| Face | Drawn in | Width, mean / worst | Signed: labels, sentences, digits, capitals | Cap height | x-height | Baseline (Avalonia − baseweb.design) |
|---|---|---|---|---|---|---|
| UberMoveText 400 | Instrument Sans Regular | 1.0% / +5.3% (the capital alphabet) | +0.0%, −0.7%, +1.8%, +4.4% | 0.720 em, +2.9% | 0.510 em, −3.2% | +0.04 to +0.76 px; the font's share +0.05 to +0.08 |
| UberMoveText 500 | Instrument Sans Medium | 1.2% / +3.4% (the capital alphabet) | −0.7%, −1.6%, −0.9%, +2.7% | 0.720 em, +2.9% | 0.510 em, −3.6% | as above |
| UberMove 700 | Figtree Bold | 1.4% / +3.7% ("Tertiary") | +0.8%, +1.1%, +0.9%, +2.9% | 0.701 em, +0.1% | 0.500 em, −3.3% | −0.40 to +0.60 px; the font's share −0.11 to −0.53 |

- **A Button's label** (UberMoveText 500 at 12 to 18 px) is within 0.53 px of baseweb.design's on
  average over the twelve labels and four sizes, and at worst 1.11 px narrower; Inter was 1.05 px
  off on average and 2.58 px at worst. "Button" at 16 px: 51.41 px against 52.25.
- **Capitals are wide** in both substitutes (+2.7% to +4.4%): an all-caps string is about 3% wider
  than baseweb.design's.
- **The x-height is 3 to 4% short** in both; caps are 2.9% tall in Instrument Sans. Text looks a
  little smaller in lowercase than Uber Move's.
- **The baseline.** Most of the difference is Chromium's, not the font's: Chromium rounds a font's
  ascent and descent to whole pixels, Avalonia doesn't. Uber Move placed as Avalonia places text
  would itself sit up to 0.8 px off baseweb.design's. The font's own share is under 0.1 px for the
  text ramp, and −0.11 to −0.53 px for the display ramp (−0.53 at 96 px).
- **Stroke weight is not measured**, only widths and heights. By width alone Figtree's 600 is
  nearer than its 700 to the file baseweb.design draws for UberMove 700 (its Bold, registered at
  600); Base Web asks 700, and Figtree's 700 is within 1.4%, so 700 stays.
- **UberMoveMono** (the Mono styles' family, `UberMoveMono, "Lucida Console", Monaco, monospace`)
  has no substitute: it wasn't measured, and no mono font is embedded. Mono text draws in Lucida
  Console or Monaco where they exist, else in the default family (Instrument Sans in the sample,
  the platform's in the tests), which isn't monospaced.
- **Scripts**: the measured strings are Latin. Both fonts map Latin-1 and Latin Extended-A, and
  neither Greek, Cyrillic nor Vietnamese (checked in their `cmap`); Avalonia falls back per
  character for those, to a font of another width.

## Consequences

- One test changed premise: `ButtonPartsTests.Filled_the_end_enhancer_sits_at_the_end_and_the_content_in_the_middle`
  expected the label centred to 0.05 px, which held only because Inter left an even room. With
  layout rounding at scaling 1, a half-pixel centre lands on a whole pixel; the test now expects
  the label on a whole pixel, on the centre when it is whole and on either pixel beside it when it
  is a half. No expected value is re-recorded from Avalonia.
- `Typography/FontSubstituteTests` checks that every ramp token's family, at its weight, resolves
  to the substitute face of exactly that weight, unsynthesised, that a Button's label draws in
  Instrument Sans at `LabelMedium`'s weight, and that a family with no mapping doesn't (the default
  isn't a substitute).
- Avalonia lays out these fonts as Chromium does: checked once with a temporary headless test, the
  21 strings' widths agree to under 0.001% at all three faces, and Avalonia's ascent (0.970 em,
  OS/2 typo) is the one Chromium used.
- Shipping the fonts in a package is not decided. Today only the tests and the sample embed them.
  A theme package that carries them would carry OFL-1.1 beside MIT, as Cornflower's does.

## Not verified

- **Other platforms.** Measured on Windows. Chromium on Windows takes a font's OS/2 typo metrics
  when `USE_TYPO_METRICS` is set and its win metrics otherwise (Roboto's matched win exactly);
  elsewhere it takes `hhea`. Uber Move's tables were never read, so whether baseweb.design's
  baseline moves on macOS, Linux or a phone is not known. The widths don't depend on it.
- **The strings** are representative, not Base Web's own copy; another set would move the
  percentages, not, at these margins, the order of the leaders.

## Reproducing

```sh
npm install
npx playwright-core install chromium   # if no Chromium is installed for playwright-core
node tools/reference/fonts.js          # the tables
node tools/reference/fonts.js --write  # and tools/reference/fonts.g.json
```

`fonts.g.json` records the platform it was measured on (`browser`); these tables are from Windows. A
run elsewhere may move the baselines (above), so compare it with a Windows run before replacing the
file. CI doesn't run the tool: it needs the network and a Chromium.
